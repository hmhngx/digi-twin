### 4. Grafana dashboard — **FIXED-THIS-SESSION (root cause found and resolved, confirmed at the data layer; visual confirmation still pending user's own check in Edge)**

**Final update:** root cause found and fixed. The user checked in real Edge (not automation) and got a genuinely useful signal that my own browser tooling never produced: Edge's DevTools console showed the panels **were** issuing their queries (`POST /api/ds/query?ds_type=influxdb`, repeating every refresh cycle), but every single one came back **`400 Bad Request`**. That's a completely different, far more diagnosable symptom than what I'd found earlier (0 requests, 0 errors, in the embedded preview browser) — and it turned out the embedded browser's silence and Edge's 400s are two **separate, unrelated** problems.

**Root cause, confirmed by direct query replay against the live datasource:**
- Replaying panel 1's exact stored Flux query returned `{"results":{"A":{"error":"max series limit exceeded (count is 1001)", ...}}}`.
- Queried `schema.tagValues(bucket: "default", tag: "correlationId") |> count()` → **27,355 distinct values**. `correlationId` is a random UUID Telegraf copies from Ditto's protocol envelope header into an InfluxDB **tag** (not a field) on every single ingested point (see `notes/twin_design_spec.md`'s Telegraf tag-mapping section, written earlier and independently of this bug). Flux/InfluxDB treats each unique tag-value combination as a separate "series." Since every PATCH gets a fresh correlationId, this is effectively one series per data point ever written — and after 17+ days of continuous `publisher.py`/`aggregator.py` activity, that number blew past InfluxDB's default 1001-series-per-query safety cap. None of the 4 panel queries had a `group()` step to collapse down to the tags that actually matter (`thingId`), so each one tried to build 1000+ series and got rejected.
- This is a **time-bomb bug**, not something that was ever going to be caught by a quick smoke test right after deploy — it only manifests once enough historical data accumulates, which is exactly why earlier "PASS WITH CAVEAT" verdicts on this dashboard (from sessions closer to the original 2026-07-26 deploy) were plausible and not dishonest at the time.

**Fix, tested and confirmed working:** added `|> group(columns: ["thingId", "_field"])` before each panel's `aggregateWindow()`/`last()` call, collapsing the high-cardinality `correlationId`-keyed series down to one series per `thingId` (which is what every panel actually wants). Verified this fix with a direct, isolated `/api/ds/query` replay for **all 4 panels individually** before touching anything live — all 4 returned `HTTP 200` with correct data (panel 4, the table, now also correctly returns exactly one row per node instead of one row per historical PATCH event, which was a second, related correctness bug the same missing `group()` was causing).
- Pushed the fix to the **live** dashboard via `POST /api/dashboards/db` (`overwrite: true`) — response `{"status":"success","version":2}`.
- Applied the identical fix to **`grafana/dashboard.json`** in the repo (all 4 panel queries), so a future re-import doesn't reintroduce the bug.
- **Visually confirmed working by the user in real Edge (screenshot provided), this session.** All 3 timeseries panels (per-node CPU, per-rack avg, cluster avg) render correctly with real live data, distinct per-series lines, correct legends. `node_0` sitting flat near 95-100% in the screenshot is **expected**, not a bug — that's `publisher.py`'s deliberate 6-minute CPU ramp (`progress = min(1.0, elapsed/360.0)`) having already reached its ceiling given how long the publisher had been running by the time of the screenshot.

**Second bug found and fixed from that same screenshot:** the table panel ("Current node state") was showing the `thingId` baked into the column headers themselves (e.g. "CPU % hnguyen.clustertwin:node_0") with only one row visible, instead of one clean row per node. ### 5. Race conditions — **PASS, verified by full code read (not just an observed run)**

Read `twin/publisher.py`, `twin/aggregator.py`, `twin/failure_detector.py`, and `twin/ditto_client.py` in full this session.

**(a) Failure detector "resume" vs publisher's next update.** Not a race, because the premise doesn't hold: `failure_detector.py` **never writes Ditto features at all**. On timeout it only logs `FAILED` and writes to a local `notes/_failure_state.json` audit file; "holding last-known values" is passive (the publisher independently skips PATCHing nodes listed in `notes/_paused_nodes.json`). `_paused_nodes.json` is written **only** by a one-shot CLI invocation (`failure_detector.py --pause/--resume`), never by the running detection loop — so there is no writer racing another writer. The only real effect is bounded polling latency: after a manual resume, the publisher notices on its next ~3s cycle and the detector notices on its next ~2s poll. That's staleness, not a race, and it's inherent to any polling design, not a bug.

**(b) Aggregator rack→cluster read ordering.** Not a race, because `aggregator.py`'s `run()` loop is single-threaded and fully synchronous: `for rid in RACK_IDS: aggregate_rack(rid)` (blocking HTTP PATCH per rack) runs to completion, **then** `aggregate_cluster_from_racks()` runs its GETs. There is no concurrency inside one cycle — the cluster-level GET is issued strictly after both rack PATCHes have received their HTTP responses, in the same Python call stack, same iteration. The only assumption this relies on is that Ditto's Things service applies a PATCH to its in-memory actor state before returning the HTTP response (standard for Ditto's per-Thing actor model) — I did not instrument Ditto internals to prove this at the framework level, but the live aggregator log obtained this session shows exactly the expected same-cycle behavior (`RACK rack_0: avg_cpu=46.32 ... RACK rack_1: avg_cpu=29.17 ... CLUSTER: avg_cpu=37.75 (from racks [46.32, 29.17])` — the cluster value is the true mean of the two numbers just printed, not stale ones).

**No code changes were made** — both hypothesized races are structurally absent given the current single-threaded, synchronous design, not races that happened not to fire during one lucky test run.

Restarted all four and confirmed each with both a raw port check and an actual HTTP request (`/api/health`, `/health`, `/docs`), not just "port is listening." **Recommendation: before any live demo, don't trust that port-forwards from earlier in the day are still up — re-check all 5 explicitly (commands in the runbook Section 1) immediately before presenting, not just once at the start of the session.** Note this did **not** affect the live publisher→Ditto→MQTT→Telegraf→InfluxDB pipeline itself, since Telegraf/Mosquitto communicate cluster-internally — it only broke *my own local access* to Grafana/InfluxDB/Extended API/Mosquitto from outside the cluster.

7b. **Update to 7a — the port-forward deaths were worse and faster than first reported, root cause likely identified.** After restarting all 5 port-forwards and reporting them healthy, all 5 died **again within minutes**, not "over 1.5 hours" — confirmed via `Get-Process kubectl` returning **zero** processes (they had fully exited, not just gone stale), while `minikube status` and every pod remained perfectly healthy throughout. This happened immediately after I'd restarted `aggregator.py` as its own new background task. Pattern observed: every time a new background process was started in this session, one or more *older* background processes (port-forwards, previously) went silently dead shortly after — consistent with this execution environment enforcing a cap on concurrent background/sandboxed processes and evicting older ones rather than the port-forwards failing for cluster/network reasons. **Not confirmed as the definitive root cause** — I could not inspect the harness's internals to prove it — but the fix based on this hypothesis worked: I consolidated all 5 `kubectl port-forward` processes into a single background task (one shell script backgrounding all 5 with `&` and `wait`, instead of 5 separate tracked background tasks), which immediately stabilized things — confirmed listening and responding, then re-checked several minutes later (publisher reached cycle 48, aggregator still recomputing normally) with no further deaths. **Recommendation for the actual meeting:** if you start port-forwards and application scripts from separate terminal windows/processes (the normal, non-agent way — i.e., what you'll actually be doing), this specific failure mode (background task eviction) does not apply to you; it was likely an artifact of how many concurrent background processes I personally was managing through the agent tooling this session, not a property of minikube, Ditto, or this repo's code. Still: the underlying lesson — **verify all 5 ports individually with a real request, not just once at the start of the day** — remains good practice regardless of cause.

7c. **Update to 7a/7b — this recurred three more times (5 total this session), including with no new background task as a trigger, and this session's operating model was changed as a result.** After the "consolidated into one task" fix in 7b, the same crash pattern (all 3 Python scripts and/or all 5 port-forwards dying together — `ConnectionResetError` / `ReadTimeout`, pods staying perfectly healthy throughout) recurred multiple more times, including at least once with **no new background task started immediately before it**, which weakens the "background task eviction" theory from 7b as the sole/complete explanation — something about this environment's long-running `kubectl port-forward` tunnels over Docker-driver minikube on Windows appears to simply be fragile over time, for reasons not fully root-caused. Given the frequency, I stopped manually restarting each one-shot process on every crash and instead relaunched **all 5 port-forwards and all 3 application scripts under `while true; do <command>; sleep 2; done` self-restarting supervisor loops**. Verified working live: `failure_detector.py` crashed once during a subsequent port-forward restart and the supervisor loop brought it back automatically within 2 seconds, no manual intervention needed. **Updated recommendation for the actual meeting: don't run these as bare one-shot commands the way `twin/README.md`'s "Cold start reproduce" section currently shows.** Wrap each in a retry loop (PowerShell: `while ($true) { <command>; Start-Sleep -Seconds 2 }`) so a transient blip during the demo doesn't silently kill the pipeline mid-presentation. **This is a real repo/README gap, not fixed this session** — `twin/README.md` still shows the fragile bare form; updating it would be a good five-minute addition before the meeting if there's time.
