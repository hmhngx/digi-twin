## Part 4 — Does the recommendation still hold up?

**Yes, with corrections.** None of the errors found change the underlying judgment that a Raspberry Pi 5 maps cleanly onto this repo's existing Node abstraction better than the ESP32 or Pi Zero cluster alternatives — that comparative reasoning wasn't touched by anything I found wrong. What *does* change is the **implementation plan**, because two of the PDF's technical claims about *how* to wire it up are incorrect (Extended API mischaracterization; the phantom "9-second aggregation window"), and a third (the exact live-message HTTP mechanism) couldn't be verified at all.

## Part 5 — Final recommendation

**Sound, with caveats — not a clean endorsement of the PDF as delivered.**

The underlying hardware judgment (Raspberry Pi 5 over the ESP32 rig or Pi Zero cluster, for *this specific repository's* reuse goals) holds up under everything checked this session — nothing found contradicts the comparative reasoning. But the PDF is not a reliable document to hand someone as-is: it contains at least one confirmed, self-contradicting factual error about its own subject (Extended API vs. core API), one internal numeric contradiction (7s vs. 9s "aggregation window"), a bibliography where roughly 40% of entries are never actually cited to a claim, and at least three citations (a personal fork, an unrelated LLM-benchmarking site, an unrelated ML-research repo) that are either wrong or nonsensical. A document with this citation failure rate earns extra scrutiny on the claims this session *couldn't* independently check, not the benefit of the doubt.

**My own confidence, independent of the PDF's claimed 95%:** moderate-to-high on the hardware choice itself (most verifiable claims held up, and nothing found overturns the Pi 5's fit); markedly lower on the PDF's implementation plan as literally written, since two of its concrete technical mechanisms are wrong or unverified. I'd put the hardware decision itself around 70–75% confidence, not 95% — the gap is entirely the PDF's demonstrated unreliability as a source plus genuine unbuilt-from-scratch risk in the actuation/control-loop path, not new doubt about the Pi 5 as a device.

**Single highest-risk unverified assumption remaining:** the exact HTTP mechanism for sending a command from the cloud side to one specific physical device via Ditto. This session confirmed the general concept (Ditto's Messages/live-channel capability) is real, but not the literal endpoint/verb the PDF names. Part 4's plan deliberately routes around this by using a plain feature-PATCH instead — but if anyone insists on using Ditto's actual live-message machinery rather than that workaround, that mechanism itself needs to be verified against the (unfetched) HTTP Messages API doc page before being relied on.

**Questions worth bringing to Prof. Siddiqui** (named in `notes/FINAL_GATE_SUMMARY.md:3`), tied to genuine open uncertainty surfaced above, not generic ones:

1. Given this repo's own documented history of long-running-process fragility (port-forward deaths, unhandled Ditto-disconnect crashes) even in the pure-software phase, is a single physical device running under a supervised/auto-restarting process an acceptable Fall-semester scope — or does the hardware phase's mandate expect real resilience engineering (retry/backoff) as a deliverable in its own right?
2. The PID/MPC thermal-control experiment requires building a genuinely new component — nothing resembling a controller exists in this codebase today. Should Fall 2026 be scoped around getting *one* clean bidirectional loop working (temperature → cloud → fan command) as the primary deliverable, with formal PID/MPC tuning and the "beat the firmware's heuristic" statistical experiment treated as a stretch goal rather than a requirement?
3. The Pi 5's `active_connections` and `latency_ms` features (part of the existing NodeType schema) have no natural physical analog once a node is a real device rather than a synthetic generator — a gap the PDF's own mapping table never addresses. Should these be dropped for the physical node, left synthetic alongside the new real features, or replaced — i.e., how literally does a physical Node's feature set need to match the existing synthetic NodeType for the composition/type graph to still count as "the same type"?
