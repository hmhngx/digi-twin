# Pi sensor accuracy and twin step-response protocol

Written 2026-10-13. A protocol for a run that has not happened: nothing below has been measured on the Pi. Companion notes: `notes/PI_TELEMETRY_SPEC_2026-10-11.md` (definitions, §5 and §11) and `notes/PI_RUNS_2026-10-12_DRYRUN_AND_LIVE.md` (the first two runs). Tools: `pi/stimulus.py`, `pi/reference_logger.py`, `scripts/analyze_accuracy.py`.

Source tags, as in the run note: **[analyzer]** printed by `scripts/analyze_pi_run.py` on a raw log; **[recomputed]** recomputed from a raw log by a throwaway script; **[user-reported, not on disk]**. From the spec: **[device]** read from the real board on 2026-10-11; **[docs]** read from official Raspberry Pi documentation (spec §11); **[repo]** read from this repo; **[design]** a decision made here, not a measurement; **[unverified]** not checked.

## 1. What this can and cannot show

**It can show** whether the sender's reading and timestamp path agrees with an independent reader of the same sources, and how the twin's value follows a load step in time.

**It cannot show absolute accuracy.** Only two quantities have a ground truth, and only by construction of the load generator: CPU (a known duty cycle) and memory (a known allocation). Frequency and temperature are two software paths to the same sensor or driver: they check the sender's read and timestamp path, **not** whether the number is right. Every output of the analyzer says, per quantity, whether its reference path differs from the sender's.

| Quantity | Sender reads | Reference reads | Reference path vs the sender's | Ground truth |
|---|---|---|---|---|
| CPU utilisation | `/proc/stat`, 2 reads, 3 s window | `/proc/stat` cumulative counters at 1 Hz, interpolated at the window edges | **same kernel file**, independent code and timestamps | by construction, for the increase over the preceding idle phase that the stimulus adds (achieved duty per worker); the raw whole-machine CPU also includes background load |
| Memory | `/proc/meminfo`: (MemTotal − MemAvailable) / MemTotal | `/proc/meminfo` raw fields at 1 Hz | **same kernel file**, independent code | by construction: the stimulus allocation (VmRSS growth) |
| Frequency | `scaling_cur_freq` | `cpuinfo_cur_freq` at 1 Hz (may be unreadable without root: then null), and `vcgencmd measure_clock arm` every 10 s | **different** sysfs file, same cpufreq driver; and a firmware path | **none** |
| Temperature | `thermal_zone0/temp` | `thermal_zone0/temp` at 1 Hz, and `vcgencmd measure_temp` every 10 s | the sysfs reference is the **same file**; vcgencmd is a different software path to the same sensor | **none** |

Which of these paths is really independent of which is a property of the Pi's kernel and firmware and is **[unverified]** here.

## 2. The load (`pi/stimulus.py`)

- CPU: 4 worker processes, each pinned to one core with `os.sched_setaffinity`, niced +10, each spinning `level` % of every 100 ms period and sleeping the rest (level 100 never sleeps). Level is the percent of **total** capacity only if workers = cores; the log records `n_cpus`, the cores actually obtained, and the duty each worker achieved. `achieved_total_percent` is relative to **all** cpus, like the aggregate in `/proc/stat`. The workers are niced, so their time is in the `nice` column of `/proc/stat`; the sender's CPU definition counts `nice` as busy (spec §5 [repo]). The workers exist for the whole run and wake every 100 ms even in idle and memory phases, so those phases are not perfectly idle, and a CPU step lags its phase stamp by up to one 100 ms period (a worker reads the level once per period).
- Memory: a `bytearray` of `level` MiB with one byte written per 4096-byte page, held for the phase; the log records VmRSS at mid-phase and how long the allocation took. A memory phase is stamped before its allocation and holds for `duration_s` after it, so the step takes the allocation time to appear; the analyzer prints that time next to the step response.
- Safety: a memory phase is refused unless MemAvailable minus the request leaves at least 200 MiB (checked for the whole schedule before anything starts, and again when each memory phase is about to begin); a hard cap on total schedule duration; SIGINT, SIGTERM and SIGHUP (a dropped SSH session) stop the workers, free the memory and write the end event, noticed within 0.2 s except during a memory allocation, which cannot be interrupted; a worker exits if its parent disappears; a thermal stop at 80 °C during CPU phases (a safety stop, **not** a measurement threshold: 80 °C is where progressive throttling of the ARM cores begins, while the soft limit, where the clock drops from 1.4 GHz to 1.2 GHz, is 60 °C, spec §11 [docs]). The safety values can only be made stricter on the command line: the reserve cannot go below 200 MiB, the thermal stop cannot go above 80 °C. The output file is created exclusively and never overwritten. From the 2026-10-11 capture, MemAvailable was 638312 kB of 926764 kB [device], so the 300 MiB step is allowed on an idle Pi and would be refused if much less memory were free.

## 3. The reference logger (`pi/reference_logger.py`)

Imports neither the sender nor the shared protocol code (a test asserts it). Raw values only: every field of each `cpu` line of `/proc/stat`, every `/proc/meminfo` field, `cpuinfo_cur_freq`, `thermal_zone0` type and temperature in millidegrees, and every 10 s `vcgencmd measure_clock arm` and `measure_temp` (skipped cleanly if `vcgencmd` is missing; the number of calls is logged). Pi wall-clock and monotonic stamps, taken right after the `/proc/stat` read; JSONL, exclusive create, flushed per line, `fsync` every 10 lines. A missing or unreadable source gives null plus an error string. **Its own CPU cost is unmeasured**; every record carries its `process_time_s`, and the `vcgencmd` subprocess every 10 s adds CPU in that second. A hung `vcgencmd` can delay one sample by up to 6 s. `cpuinfo_cur_freq` may be readable by root only **[unverified]**: if so, the 1 Hz frequency series is null with an error string and only the 0.1 Hz `vcgencmd` reference remains; the logger is not to be run as root to get it (section 7 gives the shakedown check and the fallback).

## 4. The schedule (`pi/stimulus_schedule.example.json`)

[design] 33 minutes of load: idle 5 min first (fixed); then two repetitions of seven activities, each 90 s followed by 30 s idle: CPU 25 / 50 / 75 / 100 % and memory 100 / 200 / 300 MiB. Each activity stays glued to its idle phase when the order is shuffled with a recorded seed (`--shuffle-seed N`; `--print-plan` shows the plan and total without starting anything). The idle phases give every step a baseline to start from. A run takes about 33 minutes plus a 30 s lead-in and a 60 s tail.

## 5. Definitions

- **Steady state:** the first 2 sender windows (6 s) after each phase boundary are excluded, and a CPU window must lie entirely inside the phase. Instant values on a phase boundary belong to the next phase.
- **Error:** sender value minus reference value. Per quantity and phase: n, bias (mean), mean absolute error, p95 absolute error (nearest-rank, as the existing analyzer).
- **CPU reference:** the cumulative counters linearly interpolated at `[measured_at − window_ms, measured_at]`, with the sender's CPU definition applied (spec §5); the largest interpolation gap used is reported. A CPU message without a usable `window_ms` (missing, zero, negative or not a number) is excluded and counted, never given a default window. **Bad counter reads:** a single out-of-line read (high or low) is dropped as an outlier and costs only a wider interpolation gap; a restart of the counters (a reboot) or a CPU going offline (its ticks leave the aggregate line) starts a new segment, and a window that touches the break is unusable. Dropped records, resets and unusable windows are all counted and printed; nothing after a bad read is discarded. **Memory, frequency, temperature:** the reference value nearest in time (memory percent derived with the sender's definition); the time distance is reported. There are two pre-registered distance limits, one for the 1 Hz references and one for the 10 s `vcgencmd` references.
- **Reference versus the stimulus:** CPU as the **increase over the preceding idle phase** (the reference's increase against the achieved duty's increase), which cancels a background load that is steady between the two phases; the **raw** numbers are printed beside it, labelled as including background load (the sender, the logger, the kernel), and in an idle phase the raw difference is exactly that background. With no preceding idle phase the increase is N/A and the verdict uses the raw numbers, labelled. The increase does not cancel background that changes between phases (the sender's once-a-minute work, the logger's `vcgencmd` call, other processes). Memory growth over the preceding idle phase is compared with the VmRSS growth of the stimulus process. Both are also reported against the nominal level.
- **Step response (CPU and memory only):** from a phase start to the first sender message past the **midpoint** between the previous phase's plateau and this phase's plateau, on the Pi clock via `measured_at`, and as the twin sees it via `patched_at` minus the clock offset (from the first crossing message that Ditto acknowledged; a dry run has no `patched_at`). The midpoint equals "50 % of the phase's level" only when the previous plateau is 0, which is not exactly so for CPU and not at all for memory (an idle Pi already used 19.44–20.22 % of its memory in the live run [recomputed], and 31 % in the 2026-10-11 capture [device]); it is a deliberate reading of that wording. With no previous plateau, or no step, the analyzer says N/A and computes nothing. `patched_at` is Ditto's acknowledgement, not visibility further downstream. The sender's CPU value averages the last 3000 ms, so the earliest possible crossing of the midpoint is about 1.5 s after the step; this is a property of the sender, not a defect. Temperature is excluded (thermal inertia); frequency is not controlled by the stimulus.

## 6. Thresholds are pre-registered

**The thresholds must be committed BEFORE the run.** Copy `scripts/accuracy_thresholds.template.json`, fill in every value, commit the file, and only then start the run; the analyzer prints the file's SHA-256 so the committed file can be matched to the analysis. No value is suggested anywhere, on purpose. `scripts/analyze_accuracy.py` refuses to run while any threshold is null unless `--exploratory` is given, and then it prints `EXPLORATORY: NO PRE-REGISTERED THRESHOLDS` at the top of the output and before every section, and gives no verdicts. The file has 20 fields, among them `max_instant_distance_1hz_ms` and `max_instant_distance_10s_ms`. A threshold chosen after seeing the data is not a threshold.

## 7. Procedure

0. **Shakedown on the Pi, as the normal user** (not root). Check that `vcgencmd` exists and that `vcgencmd get_throttled` answers. Run `ls -l /sys/devices/system/cpu/cpu0/cpufreq/cpuinfo_cur_freq` and a plain `cat` of it. If the `cat` fails, the 1 Hz frequency reference is recorded as null and `vcgencmd measure_clock arm` (every 10 s) is the frequency reference; **do not run the logger as root** to get it. Mode and owner on the Pi are **[unverified]** until this check is done.
1. Commit the filled thresholds file (section 6). Choose the shuffle seed and write it down.
2. Run the sender from commit 7817f4a or later; the earlier sender adds its own once-a-minute CPU bump (run note §7.1). Start the receiver as for the live run.
3. On the Pi, inside `tmux` or under `nohup` (a dropped SSH session sends SIGHUP; both tools then stop cleanly, but the run is lost): `python3 pi/reference_logger.py --out reference_<name>.jsonl`; wait about 30 s; then `python3 pi/stimulus.py --schedule pi/stimulus_schedule.example.json --shuffle-seed <N> --out stimulus_<name>.jsonl`.
4. When the stimulus has finished, wait about 60 s, stop the logger (Ctrl+C), then the sender. Run `vcgencmd get_throttled` before the run and again after it, and keep both answers with the logs (bit meanings: spec §11 [docs]). The Pi 3 B+ may soft-throttle near 60 °C during the 100 % phases, which the frequency series should show; the thermal stop at 80 °C is separate and only ends the run.
5. Copy the two Pi logs to the laptop next to the receiver log and run `python scripts/analyze_accuracy.py --receiver <receiver log> --reference <reference log> --stimulus <stimulus log> --thresholds <committed thresholds>`. The exit code is 0, or 1 if any verdict is FAIL. `--skip-windows` (default 2) is not in the thresholds file: do not change it after seeing data.

All three logs use the Pi's wall clock; if it is stepped during the run, the comparison is distorted (the sender's `ntp_synchronized` flag and the clock probes are how a step would show).

## 8. Limits

- Nothing here establishes absolute accuracy (section 1).
- The sender, the reference logger and the stimulus workers all run on the machine being measured. The logger's own cost and its `vcgencmd` subprocess are unmeasured and are inside the CPU numbers; the sender's own cost is also inside them.
- Steady state only; transients are not in the error statistics.
- One device, one pair of repetitions per level: nothing generalises beyond them.
- A 100 % CPU phase may heat the SoC toward the soft limit (60 °C, where the clock drops from 1.4 GHz to 1.2 GHz, spec §11 [docs]); that would show in the frequency and temperature comparisons and is part of what is measured.
- Memory comparisons include whatever else changes MemAvailable during a phase.
- The CPU comparison with the stimulus includes background load (section 5). The reference counters are sampled at 1 Hz and interpolated linearly, so if the load changes within a second the interpolation error is counted as sender error.
- Counter handling has limits: two or more consecutive bad reads are not recognised as outliers (the first is taken as valid and the windows that touch the bad reads are wrong), and a decrease smaller than one second's increase is invisible. A bad read costs only the windows that touch it; none after it is lost.
- Twin-visible times stop at Ditto's acknowledgement (`patched_at`); Mosquitto, Telegraf and InfluxDB are not measured.

## 9. Checks so far, and what is not verified

Done off the Pi, on a Linux x86_64 machine under WSL2 (12 CPUs, Python 3.14, no cpufreq or thermal sysfs, no `vcgencmd`): the unit tests, including the real fork, pinning, SIGTERM-with-workers, SIGHUP and failed-pool-start paths; and four short runs (17 s to 75 s) of the real stimulus and the real reference logger. Those logs were kept in the session scratchpad, not in the repo, so the numbers below cannot be re-derived from the repo. In the 75 s runs, with 4 workers on 12 CPUs, the workers pinned to cores 0–3 and achieved about 51 % duty each, and a 128 MiB allocation took 173 ms [recomputed]. There was no real sender: the receiver log of the analysed run was built from the reference's own counters, so its sender-versus-reference rows (all near 0) test the analyzer on real log shapes and say nothing about the sender.

The reference-versus-stimulus comparison in the 50 % CPU phase, over three runs [recomputed]: the `nice` column (the stimulus's own workers) was 16.1 %, 16.5 % and 16.6 % of the total against an achieved 17.0 %, 16.6 % and 16.6 %; the whole-machine CPU was 24.8 %, 21.8 % and 19.6 %, against 1.5–3.4 % in the idle phases of the same runs. So the workers' own share matched the stimulus's measurement, and the aggregate exceeded it by background load that varied from run to run plus a rise during the CPU phase of about 1 to 4 points that was not investigated. That is why the comparison is labelled as including background load. A first reading of the first run alone, "the reference and the stimulus disagree", overstated it.

The analyzer's reader of the receiver log (field names taken from `twin/pi_receiver.py`) was also run, read-only, on the real live-run log of 2026-10-13: it found 853 CPU and 854 memory, temperature and frequency points, 47 valid clock probes and `patched_at` on every message [recomputed]. No comparison was computed from that log, because no stimulus or reference log overlaps it.

**[unverified] on the Pi:** all Pi runtime behaviour of the three tools (affinity, nice, `vcgencmd`, the sysfs paths and their permissions, `cpuinfo_cur_freq` readability without root); the logger's own CPU cost; the stimulus's effect on the sender and the receiver. The mapping of the receiver log was checked as described above and otherwise only on synthetic logs.
